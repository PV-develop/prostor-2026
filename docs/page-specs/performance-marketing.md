# Спецификация страницы: Performance-маркетинг

Внутренняя страница `/services/performance-marketing/`. Этот файл — единственный источник требований и контента страницы: бриф (`performance-marketing-brief.md`) и контент (`performance-marketing-content.md`) читать не требуется, вся необходимая информация продублирована ниже.

Обязательные технические источники проекта (читаются перед и во время реализации):

- `AGENTS.md` — правила проекта, дизайн-система, порядок проверки;
- `docs/blocks.md` — актуальная библиотека блоков и UI-компонентов;
- `docs/design-system.md` — документация дизайн-системы;
- существующие компоненты в `src/components/` и токены `src/styles/design-tokens.css` — как образец реализации и источник переиспользуемых паттернов.

## 1. Основные параметры страницы

| Параметр | Значение |
| --- | --- |
| URL | `/services/performance-marketing/` |
| Название | Performance-маркетинг |
| H1 | Performance-маркетинг под задачи вашего бизнеса |
| Активный пункт меню | Услуги |
| Шаблон | `BaseLayout` + `SiteHeader` + `MobileMenu` + `SiteFooter` (сквозные, не менять) |

Хаб не должен превращаться в «просто список услуг». Основная цель — продажа работы сразу с несколькими каналами через общую форму |
| Целевая аудитория | 1) Нужны лиды и продажи быстрее, чем даёт органика. 2) Реклама есть, но стоимость заявки растёт или результаты нестабильны. 3) Нужно протестировать канал, гипотезы, рынки, продукт или оффер. 4) Нужен единый подрядчик: контекст, таргет, ретаргетинг, Промостраницы, Авито, геосервисы |
| Тон | Экспертный, понятный, немного дружелюбный. Без «умничанья» |
| Основной CTA всех блоков | «Обсудить привлечение клиентов» → якорь `#contact-form` (общая форма). Второй CTA: «Получить аудит рекламы» → тот же якорь |

### Ключевые ограничения по обещаниям (обязательны для всех текстов страницы)

Не обещать:

- гарантированные продажи;
- гарантированное количество лидов;
- фиксированную стоимость заявки или продажи без анализа проекта;
- быстрые результаты;
- скидки;
- универсальные сроки запуска, минимальные бюджеты и период окупаемости без привязки к продукту.

Позиционирование: построение управляемой системы и измеримость без безусловных обещаний. Обязательный следующий шаг — брифинг/консультация, после которой принимается решение о сотрудничестве. За агентством остаётся право отказаться от проекта.

| Ситуация | Описание |

### Блок 5. Кейсы — `#cases`

- **Компонент**: `CasesSection` + `CaseCard` (библиотека). Контент — новые данные в `src/content/`.
- **Заголовок**: **Как мы решали задачи наших клиентов**
- **Состав**: 2–3 кейса с разными сценариями (улучшение существующей рекламы; запуск нового продукта/направления; увеличение объёма; несколько инструментов одновременно).
- **Карточка**: клиент и отрасль, ключевая цифра, короткое пояснение к цифре (что считали, с чем сравнивали, за какой срок), использованные инструменты (теги), что сделали/изменили, результаты и сроки. Кнопка «Смотреть кейс» выводится **только если у кейса есть реальная страница**; если страницы кейса нет — кнопка не выводится вовсе (никаких `href="#"` и мёртвых ссылок).
- **Особенности**: теги инструментов некликабельны в первой версии (нет страниц/фильтров — мёртвые ссылки запрещены). Ссылка «Все performance-кейсы» **не выводится** — страницы архива нет.
- **Контент**: ⚠️ нет подтверждённых кейсов по performance — см. раздел 6. До появления данных блок не заполняется выдуманными кейсами.
- **Desktop/mobile**: сетка как в существующем `CasesSection` (реализация уже адаптивна).

| Уровень | Что предлагаем отслеживать |

## 4. Новые и расширяемые блоки

### 4.1 Расширение существующих (не создавать копии)

**`HeroMain` → вариант внутренней страницы.** Сейчас жёстко привязан к контенту главной (подписи «20», `TrustMarquee`). Расширить типизированными props:

```ts
interface HeroMainProps {
  variant?: 'home' | 'page';   // default 'home'
  showMarquee?: boolean;       // default true; для page — false
  hero: {
    title: string;             // HTML, поддерживает <br> и stroke-спаны
    lead: string;
    note?: string;             // доп. строка («Используем собственную аналитику Prostor.»)
    primaryCta?: { label: string; href: string };
    secondaryCta?: { label: string; href: string };
    label?: string;            // вертикальная подпись, для page — опционально
  };
}
```

Частицы/параллакс из `main.ts` должны корректно работать в обоих вариантах либо отключаться для `page` — без ошибок консоли. Если расширение `HeroMain` усложнит его сверх разумного, допустимо вынести общую основу в UI и собрать hero страницы локально — решение фиксируется в код-ревью, копипаст блока запрещён.

**`ProcessSection` → табличный вариант.** Существующий блок: 5 карточек этапов. Нужна таблица «этап / что делаем / что получаете» — тот же предмет (этапы работы), тот же объём данных. Расширить:

```ts
interface ProcessSectionProps {
  variant?: 'cards' | 'table';  // default 'cards'
  heading: string;              // HTML-строка
  label?: string;
  steps: Array<{
    title: string;              // этап
    detail?: string;            // что делаем (table)
    outcome?: string;           // что получаете (table)
  }>;
}
```

Для `cards` поведение остаётся прежним (скролл-снап на ≤1024, стрелки из `main.ts`); для `table` — адаптивная таблица/список строк (на mobile строки стекаются внутри карточки этапа). Анимацию стрелок для `table` не включать.

**`ContactForm` → набор полей через props.** Сейчас поля захардкожены (имя, почта, телефон, описание, файл). Для страницы нужен другой набор (раздел 5). Расширить:

```ts
interface ContactFormProps {
  title?: string;              // HTML; default текущий
  lead?: string;
  submitLabel?: string;        // default «Отправить заявку»
  fields?: {
    name?: boolean;            // default true
    contact?: 'split' | 'single'; // split = почта+телефон (как сейчас); single = одно поле «Контакт и предпочтительный способ связи»
    email?: boolean; phone?: boolean; // при contact: 'split'
    company?: boolean;         // «Сайт или название компании»
    scenario?: { enabled: boolean; options: string[] }; // select «Сценарий/задача»
    message?: boolean;
    file?: boolean;
    statusToggle?: { enabled: boolean; options: string[] }; // «Реклама уже есть / Планируем запуск / Пока не определились»
  };
}
```

Поведение mock-отправки (`data-mock-form`) и стили сохраняются; верстка полей остаётся на `TextField`/`TextArea`/`FileField`. Для select и toggle, если нет готовых UI-компонентов, добавить минимальные стилизованные элементы на чистом CSS/TS (без библиотек) и по возможности вынести в `src/components/ui/` (`SelectField.astro`, `ToggleGroup.astro`) — см. 4.2.

## 5. Форма (одна общая на странице)

- **Расположение**: блок 11, якорь `#contact-form`, тёмная секция вместе с футером.
- **Компонент**: `ContactForm` (расширенный, см. 4.1) внутри `CtaForm`-подобной обёртки; mock-отправка по существующему паттерну `data-mock-form`.
- **Поля** (все из брифа):

| Поле | Тип | Обязательность |
| --- | --- | --- |
| Имя | `TextField` (autocomplete="name") | обязательное |
| Контакт и предпочтительный способ связи | одно текстовое поле (посетитель пишет телефон/почту/ник и способ связи) | обязательное |
| Сайт или название компании | `TextField` | необязательное |
| Сценарий/задача | `SelectField` — выпадающий список | необязательное |
| Короткое описание задачи | `TextArea` | необязательное |
| Статус рекламы | `ToggleGroup` из трёх опций: «Реклама уже есть / Планируем запуск / Пока не определились» | необязательное (выбор одного, по умолчанию не выбрано) |
| Приложить файл | `FileField` | необязательное |

- **Опции select «Сценарий/задача»**: список опций = заголовки карточек блока ScenarioGrid («Нужны целевые обращения», «Реклама есть, результат не устраивает», «Нужно проверить новое направление», «Нужно увеличить объём») + нейтральный пункт «Другое». Автоматическая подстановка выбранной карточки в форму **не реализуется** в первой версии.
- **Валидация**:
  - имя и контакт — обязательные: пустое значение блокирует отправку, поле получает состояние ошибки (акцентный цвет токенов, текст ошибки под полем);
  - для поля контакта жёсткий формат не требуется (посетитель сам указывает способ связи), но значение не должно состоять только из пробелов;
  - остальные поля без валидации;
  - ошибки сбрасываются при вводе; фокус первого ошибочного поля после неудачной отправки.
- **CTA формы**: одна кнопка отправки — **«Отправить заявку»**. Скрытые поля и любая передача сценария/варианта CTA в форму **не реализуются**: все CTA страницы (основной и дополнительный сценарии) просто прокручивают к форме по якорю `#contact-form`.
- **Поведение после отправки**: существующий mock-паттерн (успешное состояние кнопки/формы из `main.ts`), без реальной отправки на сервер.
- **Desktop**: форма и блок прямых контактов в одной строке/сетке (форма основная, контакты компактным блоком рядом или под заголовком — по сетке тёмной секции). **Mobile**: вертикальный стек, поля и кнопка во всю ширину, `FileField` и toggle не ломают раскладку.
- **Юридическая строка**: сохранить существующую строку про согласие с политикой обработки персональных данных (страницы политики пока нет — разметка с TODO сохраняется, как в текущем `ContactForm`).

## 7. Не входит в первую версию

- Автоматическая передача выбранной карточки сценария в форму.
- Внешние iframe/демо/виджеты (в т.ч. демо аналитики).
- Фрагменты реальных отчётов (даже обезличенные) — только вторая итерация после согласования.
- Кликабельные фильтры/теги кейсов и ссылка «Все performance-кейсы» — только при появлении реальных страниц.
- Отдельные страницы услуг из блока каналов и ссылки на них.
- Sticky-состояние якорной навигации при скролле.
- Визуальная схема «гипотеза → инструмент → бюджет теста → критерий решения» (опционально, вторая итерация).
- SLA в блоке процесса.
- Реальная отправка формы на сервер (mock-отправка как на главной).
