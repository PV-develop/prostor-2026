# Prostor — визуальные правки страницы Performance-маркетинга

## 1. Цель задачи

Внести согласованные визуальные изменения на странице `performance-marketing`, сохранив существующую структуру сайта, контент, SEO-настройки и функциональность.

Работать в рамках текущей архитектуры проекта и дизайн-системы Prostor. Переиспользовать существующие компоненты главной страницы там, где это соответствует задаче. Не создавать параллельную дизайн-систему.

**Главный принцип:** менять только те элементы, которые явно перечислены в этом задании. Не переписывать тексты, URL, SEO, контентные TODO и соседние секции по собственной инициативе.

## 1.1. Стратегия развития библиотеки блоков проекта — критически важный контекст

Проект развивается по принципу последовательного накопления библиотеки переиспользуемых блоков.

- **Главная страница — первый этап.** На ней сформированы базовая дизайн-система, визуальные паттерны, типографика, карточки, анимации и первые переиспользуемые компоненты.
- **Текущая внутренняя страница Performance — второй этап.** Её задача не только получить качественный дизайн, но и расширить, проверить и систематизировать библиотеку блоков проекта на реальном примере внутренней страницы.
- **Следующие внутренние страницы — третий этап.** Они должны собираться преимущественно из готовой библиотеки. Новые блоки создаются только тогда, когда подходящего решения действительно нет или существующий компонент нельзя разумно адаптировать.

Это архитектурное требование, а не пожелание.

### Как применять этот принцип в текущей задаче

1. Перед созданием любого нового блока искать подходящий компонент в существующей библиотеке и на главной странице.
2. Если подходящий компонент есть — использовать его через конфигурацию и стили, не создавать дубликат.
3. Если готового решения нет — определить, является ли новый блок типовым и потенциально полезным для других страниц.
4. Если блок может использоваться повторно — проектировать его как самостоятельный универсальный компонент библиотеки, отделяя структуру и поведение от текстов и данных конкретной страницы.
5. Если блок действительно уникален — допустима локальная реализация, но не нужно искусственно обобщать одноразовый элемент.
6. После создания нового компонента проверить его на соответствие дизайн-системе и пригодность для повторного использования.
7. Зафиксировать в итоговом отчёте, какие элементы библиотеки появились или были расширены, для каких задач они подходят и как подключаются.

### Целевой результат текущей страницы

После завершения Performance следующая внутренняя страница должна требовать минимального количества новой разработки. В идеале её можно будет собрать из существующих компонентов, меняя контент, конфигурацию, графические пресеты и порядок секций.

Не создавать библиотечные компоненты только ради формального увеличения их количества. Цель — библиотека действительно полезных, согласованных и повторно используемых блоков.

## 2. Обязательные ограничения

- Основной объект изменений — страница `performance-marketing`. Общие компоненты можно создавать или расширять, если это пополняет библиотеку блоков проекта и не вызывает регрессий на других страницах.
- Не ограничиваться локальной стилизацией секций: оценивать каждый новый тип блока с точки зрения повторного использования на следующих внутренних страницах.
- Не менять URL, SEO-метаданные, заголовки и контент за пределами явно описанных ниже изменений.
- Не удалять и не заполнять контентные TODO.
- Не менять глобальную шапку сайта и существующую функциональность CTA.
- Не менять главную страницу визуально. Если требуется переиспользовать её компонент или анимацию, сделать это без изменения поведения главной.
- Не добавлять библиотеки без технического обоснования.
- Не делать commit и push.
- Не исправлять посторонние проблемы проекта в рамках этой задачи. Если обнаружена блокирующая проблема, зафиксировать её отдельно.
- Не подменять отсутствующие требования собственными догадками. Неясные места перечислить в итоговом отчёте.

## 3. Сначала изучить проект

До внесения изменений:

1. Проверить текущую ветку, `git status` и наличие незакоммиченных изменений. Не перезаписывать чужую работу.
2. Найти реализацию страницы `performance-marketing` и всех её секций.
3. Изучить главную страницу: https://pv-develop.github.io/prostor-2026/
4. Найти и изучить на главной:
   - блок «С какой задачей требуется помощь?»;
   - блок «Как мы выстраиваем работу» / карточки этапов;
   - существующую анимацию частиц;
   - шапку сайта и нижнюю навигацию.
5. Проверить используемые компоненты, стили, CSS-переменные, шрифты, брейкпоинты и правила адаптивности.
6. Установить, какие элементы можно переиспользовать напрямую, а какие нужно обобщить.

**До реализации составить короткий план:** какие файлы и компоненты предполагается изменить, что будет переиспользовано и какие риски есть. Не начинать массовый рефакторинг до этого анализа.

# 4. Требования по блокам

## 4.1. Hero и in-page меню

<badge>Приоритет 1 · Сложная архитектурная задача</badge>

### Цель

Переработать первый экран страницы Performance-маркетинга и подготовить универсальный шаблон Hero для других одноуровневых страниц. Визуальная идея — Generative Visual Identity: абстрактная графическая композиция из частиц, которая собирается в форму, связанную с тематикой страницы.

### Что сохранить

- Тёмный фон.
- Существующую глобальную шапку, логотип и навигацию.
- Крупный заголовок слева с узкой акцидентной типографикой.
- Возможность выделять отдельные слова контурным начертанием.
- Описание направления справа.
- Основную и дополнительную CTA.
- Нижнее in-page меню.
- Тексты, URL и действия существующих CTA.

Не менять содержание Hero без отдельного согласования.

### Новая графическая композиция

Добавить крупный абстрактный графический объект из частиц. Он должен быть интегрирован в композицию Hero, а не выглядеть как случайная иллюстрация, помещённая в свободное место.

Графический объект может частично пересекаться с областью заголовка, только если это не ухудшает читаемость.

Визуальный характер:
- чёрный фон;
- преимущественно белые частицы;
- небольшое количество красных акцентных частиц;
- разный размер и прозрачность элементов;
- тонкие связи между отдельными частицами;
- ощущение глубины и пространства;
- плавное, органичное движение.

Избегать шаблонных AI-сетей, типовых 3D-сфер и буквальных изображений рекламных кабинетов, графиков или объявлений.

### Анимация

При первом появлении Hero:
1. Частицы появляются вокруг будущей формы.
2. Двигаются по индивидуальным траекториям.
3. Постепенно собираются в заданную геометрию.
4. Формируют цельную композицию.
5. После сборки продолжают медленно двигаться, сохраняя общую форму.

Не запускать постоянное разрушение и повторную сборку объекта.

Предусмотреть деликатную реакцию частиц на курсор с плавным возвратом в исходное состояние. На мобильных устройствах реакцию на курсор отключить.

### Пресет Performance-маркетинга

Для первой реализации использовать образ **сети рекламных каналов и потоков данных**:
- несколько выраженных узлов;
- множество связей между ними;
- неоднородная плотность частиц;
- отдельные потоки, направленные к центральным точкам;
- ощущение единой системы из взаимодействующих элементов.

Другие направления — SEO, аналитика, AI, разработка, репутация — пока не реализовывать. Только предусмотреть возможность добавлять для них отдельные конфигурации в будущем.

### Универсальная архитектура

Создать переиспользуемый компонент `ServiceHero` либо обобщить существующий, если в проекте уже есть подходящая архитектура.

Предусмотреть конфигурацию:
- `eyebrow` — маркер / название направления;
- `title` — заголовок;
- `accentText` — фрагмент заголовка с контурным оформлением;
- `description` — описание;
- `additionalLabel` — дополнительная метка;
- `primaryCTA` — основная CTA;
- `secondaryCTA` — дополнительная CTA;
- `visualPreset` — конфигурация графического объекта;
- `navigationItems` — пункты внутренней навигации.

Графический движок должен быть независим от контента Hero. Новую страницу должно быть возможно подключить через конфигурацию, не создавая отдельную реализацию компонента.

Не создавать новый компонент, если аналогичный уже существует и его можно безопасно расширить.

**Важно для библиотеки:** `ServiceHero` должен быть пригоден для подключения на других одноуровневых страницах через конфигурацию. Не зашивать в него тексты, CTA, якоря и графическую композицию, специфичные только для Performance. При этом не нужно заранее реализовывать все будущие направления — достаточно заложить чистую точку расширения для новых `visualPreset`.

### Производительность

Сначала изучить существующую анимацию частиц на главной. По возможности переиспользовать её механику или движок, не меняя визуальное поведение главной страницы.

Технические требования:
- выбрать Canvas или WebGL после анализа существующего решения и реальной нагрузки;
- не добавлять тяжёлые 3D-библиотеки без необходимости;
- использовать `requestAnimationFrame` для анимационного цикла, если выбранная технология этого требует;
- адаптировать число частиц под возможности устройства;
- приостанавливать анимацию, когда Hero не виден;
- учитывать `prefers-reduced-motion`;
- предусмотреть статическое состояние при отключённой анимации или её неподдержке;
- не ухудшать прокрутку и отзывчивость страницы.

### In-page меню

Сохранить текущий визуальный язык и оформить меню как отдельный переиспользуемый компонент.

Функциональность:
- пункты формируются из разделов конкретной страницы;
- каждый пункт ведёт к соответствующей секции;
- активный раздел определяется при прокрутке;
- активный пункт выделяется красным;
- переход к секции плавный;
- при переходе учитывать высоту закреплённого меню;
- заголовки секций не должны скрываться под меню;
- поддерживается разное количество пунктов.

Desktop:
- горизонтальное меню в нижней части экрана;
- закрепление при прокрутке, если это соответствует текущей механике страницы.

Mobile:
- горизонтальная прокрутка пунктов;
- активный пункт автоматически остаётся видимым;
- пункты не переносятся на вторую строку;
- горизонтальная прокрутка не должна появляться у всей страницы.

### Адаптивность Hero

Desktop:
- крупная генеративная графика;
- заголовок и описание в двухколоночной композиции;
- графика занимает заметную часть свободного пространства.

Tablet:
- адаптировать размеры заголовка и графики;
- сохранить иерархию;
- при необходимости сместить графику ниже.

Mobile:
- заголовок и описание располагаются вертикально;
- графика занимает отдельную область и не мешает CTA;
- количество частиц уменьшается;
- реакция на курсор отключена;
- сохраняется выразительность первого экрана.

## 4.2. Блок «Задачи» (`#tasks`)

### Цель

Переработать блок, используя в качестве визуального ориентира главную секцию «С какой задачей требуется помощь?».

Новая композиция — две колонки: смысловой заголовок и пояснение слева, список из четырёх сценариев справа.

### Левая колонка — около 35%

- Маркер раздела «Задачи» с красным акцентом.
- Заголовок: **«КОГДА БИЗНЕСУ НУЖНА РАБОТА С PERFORMANCE-РЕКЛАМОЙ»**.
- Пояснение: «Четыре ситуации, в которых performance-реклама помогает найти точки роста».
- Колонка должна иметь самостоятельную визуальную структуру.

### Правая колонка — около 65%

Разместить четыре сценария вертикальным списком вместо текущих карточек.

Каждая строка:
- номер 01–04;
- заголовок;
- описание под заголовком;
- небольшая графическая метка или стрелка справа;
- тонкий разделитель между строками.

### Тексты

**01. НУЖНЫ ЦЕЛЕВЫЕ ОБРАЩЕНИЯ**  
Определить, какие рекламные инструменты стоит проверить для вашего продукта и аудитории.

**02. РЕКЛАМА ЕСТЬ, РЕЗУЛЬТАТ НЕ УСТРАИВАЕТ**  
Разобраться, где теряются бюджет и обращения: в настройках рекламных кампаний, предложении, посадочной странице или обработке заявок.

**03. НУЖНО ПРОВЕРИТЬ НОВОЕ НАПРАВЛЕНИЕ**  
Протестировать продукт, оффер, географию или аудиторию по заранее согласованным критериям.

**04. НУЖНО УВЕЛИЧИТЬ ОБЪЁМ**  
Найти возможности роста и оценить, как расширение повлияет на стоимость и качество привлечения.

Сохранить смысл и формулировки. Не добавлять новую функциональность строкам, если её нет в текущем блоке.

### Стиль

- светло-серый фон страницы;
- белые или слегка контрастирующие поверхности, если они нужны для композиции;
- чёрная типографика;
- красные акценты;
- существующая пара шрифтов;
- узкая акцидентная типографика заголовков.

Обеспечить адаптивность и отсутствие переполнений.

## 4.3. Блок «Каналы» (`#channels`)

### Концепция

Создать блок Advertising Toolkit — панель из пяти рекламных инструментов. На Desktop разместить пять вертикальных карточек в один ряд.

Использовать визуальный язык карточек этапов главной страницы, но адаптировать его под самостоятельные рекламные инструменты, а не копировать карточки буквально.

### Структура карточек

Каждая карточка содержит:
1. Номер канала 01–05.
2. Название рекламного инструмента.
3. Краткое описание.
4. Нижнюю информационную зону с меткой «Задача канала» и назначением инструмента.

Визуальные особенности:
- крупная типографическая нумерация;
- узкий акцидентный шрифт заголовков;
- светлая поверхность;
- минималистичные разделители;
- вертикальное распределение контента;
- нижняя зона отделена тонкой линией;
- чёткая геометрия без декоративных скруглений.

### Содержание карточек

**01. КОНТЕКСТНАЯ РЕКЛАМА**  
Запускаем и развиваем рекламу в Яндекс Директе с согласованными целями и аналитикой.

Задача канала:  
Привлечение пользователей с уже сформированным спросом.

**02. ТАРГЕТИРОВАННАЯ РЕКЛАМА**  
Настраиваем и ведём рекламу в соцсетях и мессенджерах: подбираем аудитории, тестируем объявления и отслеживаем обращения.

Задача канала:  
Формирование спроса и привлечение целевых аудиторий.

**03. ЯНДЕКС ПРОМОСТРАНИЦЫ**  
Создаём и продвигаем статьи в Яндекс Промостраницах, чтобы знакомить аудиторию с продуктом и привлекать заинтересованных пользователей на сайт.

Задача канала:  
Знакомство с продуктом через контент.

**04. АВИТО**  
Оформляем и продвигаем объявления на Авито и с помощью Авито Ads, тестируем подачу предложений и отслеживаем обращения.

Задача канала:  
Привлечение покупателей через объявления.

**05. ГЕОСЕРВИСЫ**  
Оформляем и продвигаем карточки компании в картах и геосервисах, чтобы клиентам было проще найти и выбрать вас.

Задача канала:  
Повышение локальной видимости компании.

### Композиция и адаптивность

Desktop:
- пять карточек в один ряд;
- одинаковая ширина и высота;
- равномерные промежутки;
- заголовок блока над карточками;
- карточки занимают доступную ширину контентной области.

Внутри карточки номер располагается сверху, название — ниже, описание — в центральной части, назначение канала — ближе к нижнему краю.

Tablet:
- перестроить сетку под доступную ширину;
- сохранить читаемость и согласованность карточек.

Mobile:
- вертикальное расположение или компактная сетка, если она не ухудшает читаемость;
- не допускать горизонтальной прокрутки страницы.

### Цвета и состояния

Использовать светло-серый фон, светлые карточки, чёрную типографику и красный акцент. Использовать существующие шрифты и дизайн-токены.

Допустим деликатный hover: изменение акцента или фона с плавным переходом. Не делать карточки кликабельными без существующей функциональной причины.

## 4.4. Блок «Подход» (`#approach`)

### Концепция

Сохранить редакционную таблицу с двумя колонками. Не превращать строки в карточки.

Слева показываем, что анализируем, справа — какое решение на основании этого принимаем.

### Заголовок

Сохранить текст:

**«КАК МЫ ОПРЕДЕЛЯЕМ, КУДА НАПРАВИТЬ БЮДЖЕТ»**

Сохранить маркер раздела «Подход» с красным квадратом и существующую узкую акцидентную типографику.

### Колонки

- Левая — «ЧТО ВЫЯСНЯЕМ», примерно 43%.
- Правая — «КАКОЕ РЕШЕНИЕ ПРИНИМАЕМ», примерно 57%.

Добавить тонкую вертикальную линию между колонками.

### Строки

Добавить перед каждым заголовком небольшой красный номер.

**01. ЦЕЛЬ И ЭКОНОМИКА ПРОДУКТА**  
→ Какой результат/KPI оцениваем и какую стоимость привлечения рассматриваем как ориентир.

**02. АУДИТОРИЯ И ПУТЬ ДО ПОКУПКИ**  
→ Какие точки контакта и рекламные инструменты стоит проверить.

**03. СОСТОЯНИЕ САЙТА И ОБРАБОТКИ ЗАЯВОК**  
→ Что нужно подготовить до запуска или улучшить параллельно.

**04. ДОСТУПНЫЙ БЮДЖЕТ И ДАННЫЕ**  
→ С какого набора гипотез начать, чтобы не распылять ресурсы.

**05. РЕЗУЛЬТАТЫ ТЕСТОВ**  
→ Что продолжать, пересматривать, останавливать или расширять.

### Иерархия строк

- номер 01–05 — небольшой красный акцент;
- название критерия — крупный узкий акцидентный шрифт;
- справа — красная стрелка;
- решение — обычный шрифт основного текста;
- допускается полужирное выделение ключевой смысловой части, но не всего текста;
- содержимое колонок вертикально выровнено по центру строки;
- между строками сохранены горизонтальные разделители;
- строки достаточно свободные, но не чрезмерно высокие.

### Нижний информационный блок

Сохранить текст без изменений:

«Не распределяем бюджет поровну между площадками. Сначала определяем приоритеты и критерии проверки, затем корректируем план по результатам».

Оформление:
- чёрная подложка;
- белый текст;
- тонкая красная вертикальная линия слева;
- достаточные внутренние отступы;
- удобная ширина текстового блока.

Расположить под таблицей, желательно со смещением вправо, сохранив редакционный характер композиции.

### Стиль и интерактивность

Использовать светло-серый фон, чёрную типографику, красный акцент, тонкие серые разделители и существующие шрифты.

Не добавлять градиенты, тени, скруглённые карточки, объёмные декоративные элементы и сторонние иллюстрации.

Допустим деликатный hover: усиление красного акцента номера или стрелки. Не смещать всю строку и не делать её кликабельной без соответствующей функциональности.

### Адаптивность

Desktop:
- две колонки 43/57;
- пять горизонтальных строк;
- вывод под таблицей.

Tablet:
- сохранить таблицу, адаптировать пропорции и размеры текста.

Mobile:
- каждая строка перестраивается вертикально;
- сначала номер и заголовок, ниже — стрелка и решение;
- разделители сохраняются;
- информационный блок занимает всю ширину.

Не допускать горизонтальной прокрутки и переполнения текста.

Использовать вертикальные карточки по образцу блока «Как мы выстраиваем работу» на главной странице. Если существующий компонент можно параметризовать для повторного использования, расширить его и включить в библиотеку, а не делать локальную копию.

- структуру и порядок элементов;
- типографическую иерархию;
- нумерацию;
- внутренние отступы;
- разделители;
- адаптивное поведение.

Адаптировать компонент под контент текущего блока. Не менять сам блок на главной и не нарушать его внешний вид.

Сохранить существующие тексты и содержание блока «Процесс». Не переписывать контент без отдельного указания.

# 5. Порядок выполнения работ

Работать поэтапно, не пытаться реализовать всё одним большим рефакторингом.

## Этап 1. Аудит и план

- Проверить состояние Git и незакоммиченные изменения.
- Изучить страницу, главную и существующие компоненты.
- Найти анимацию частиц.
- Составить список файлов и компонентов, которые потребуется изменить.
- Определить, какие компоненты можно переиспользовать.
- Зафиксировать риски и неясности.

После аудита сообщить краткий план. Если нет блокирующих вопросов, продолжить работу без ожидания дополнительного подтверждения.

## Этап 2. Hero и навигация

Это наиболее сложная часть и основа будущего шаблона.

- Спроектировать переиспользуемую архитектуру.
- Реализовать графический пресет Performance.
- Переиспользовать механику частиц главной, если это технически оправдано.
- Реализовать in-page меню.
- Проверить адаптивность и производительность.

Не переходить к остальным блокам, пока Hero и навигация не работают стабильно.

## Этап 3. Контентные блоки и пополнение библиотеки

Выполнить последовательно:
1. `#tasks`
2. `#channels`
3. `#approach`
4. `#process`
5. `#pricing`

Переиспользовать компоненты главной там, где это указано. Не менять содержание блоков, кроме явно приведённых текстов и структурных изменений из задания.

Для каждого блока определить один из трёх вариантов:
- **Переиспользовать** — подходящий компонент уже есть.
- **Расширить библиотеку** — подходящего компонента нет, но новый блок будет полезен на других страницах.
- **Оставить локальным** — блок специфичен для Performance и не должен искусственно превращаться в универсальный компонент.

После реализации проверить, что библиотека не содержит дублирующих компонентов с одинаковой задачей, но разной разметкой.

## Этап 4. Проверка всей страницы

Проверить:
- целостность визуальной системы;
- отсутствие конфликтов между секциями;
- правильную работу in-page меню и якорей;
- все CTA и существующие функциональные привязки;
- адаптивность;
- отсутствие горизонтальной прокрутки;
- отсутствие переполнений и наложений;
- производительность анимации;
- отсутствие регрессий на главной странице.

## Этап 5. Проверка библиотеки и технические проверки

Дополнительно проверить библиотеку:
- какие новые переиспользуемые компоненты появились;
- какие существующие компоненты были расширены;
- не появились ли дубликаты уже существующих блоков;
- можно ли подключить новые компоненты на другой внутренней странице без копирования кода;
- отделены ли данные и конфигурация страницы от структуры универсальных компонентов.


Запустить из корня проекта:

```bash
npx astro check
npm run build
```

Если одна из команд завершается ошибкой:
- определить, связана ли она с внесёнными изменениями;
- исправить регрессии, возникшие из-за текущей задачи;
- не маскировать ошибки и не менять посторонние части проекта ради формального прохождения проверки;
- зафиксировать оставшиеся ошибки в отчёте.

Проверить страницу в браузере на Desktop и Mobile. Также проверить промежуточную ширину Tablet.

Сделать актуальные скриншоты результата для сравнения с исходным состоянием. Если в проекте уже предусмотрено место или соглашение для скриншотов, использовать его; не создавать произвольную инфраструктуру.

# 6. Критерии приёмки

Работа считается выполненной, если:

- Все перечисленные блоки приведены к согласованной композиции.
- Hero использует переиспользуемую архитектуру и отдельный графический пресет.
- Анимация не ухудшает производительность и не ломает главную страницу.
- In-page меню корректно работает с разделами страницы.
- Карточки и таблица адаптируются под разные ширины экрана.
- Существующие CTA, ссылки и функциональные привязки сохранены.
- SEO, URL и контентные TODO не изменены.
- Форма осталась без изменений.
- `npx astro check` и `npm run build` выполнены, результаты отражены в отчёте.
- В Git нет созданного агентом commit или push.
